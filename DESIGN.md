# Design System

## Stack

- framework: Electron + React 19 (electron-vite) — renderer at `frontend/renderer`
- styling: Tailwind CSS 3 (`frontend/renderer/src/styles/globals.css`)
- components: custom primitives (no external component library)
- animation: CSS transitions/keyframes only (no animation library — kept the Electron bundle lean)
- icons: inline SVG (no icon library dependency)

## Path map (adapted from the `vite-react-tailwind` preset for this project's electron-vite layout)

| Resource                | Path                                                                                                                                                     |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Components (primitives) | `frontend/renderer/src/components/ui/`                                                                                                                   |
| Components (features)   | `frontend/renderer/src/components/features/`                                                                                                             |
| Utils                   | `frontend/renderer/src/lib/utils.ts`                                                                                                                     |
| Global styles           | `frontend/renderer/src/styles/globals.css`                                                                                                               |
| Tailwind config         | `tailwind.config.ts` (repo root)                                                                                                                         |
| Path alias              | `@renderer` → `frontend/renderer/src` (already defined in `electron.vite.config.ts` / `tsconfig.web.json`, reused rather than adding a second `@` alias) |

## Tokens

- brand: `#6366f1` (indigo) — same hex in light and dark, and shared by retail and wholesale
- bg-base: `#ffffff` / dark `#0f1117`
- text-primary: `#111827` / dark `#f9fafb`
- radius: 8px (`md`), 12px (`lg`)
- shadow: layered (xs–xl), see `globals.css`
- full token map in `frontend/renderer/src/styles/globals.css`

- 2026-09-11 — Delivery built, the wholesale workflow's third screen. Same shape as the first two (figure cards, one panel with header/filters/table/pagination, a detail sheet, a three-step wizard) with one deliberate difference: this detail sheet is the one you **type into**. Packages move a stop at a time, so "The journey" is a table with a row for the cargo company, a row per stop from the ERD's `shipment_leg`, and an "Arrived here" row — each carrying an editable package count and a worked-out "still there" figure. Every input is capped at what can physically be present: a stop cannot receive more than the stop before it sent on, and lowering a stop's received count pulls its sent count down with it. That is the whole point of the screen — 10 packages leave the cargo company, 7 arrive in Yangon, and the gap says exactly where they went missing rather than leaving a mystery at the end. The layout follows the prototype's Delivery page closely, because that page is doing something the other two are not. Its figure cards count shipments per state, with the state's colour in the number only — the tinted card faces the prototype uses were tried and taken off, since summary cards across this app are plain white panels. Its search, filter and New shipment controls sit in their own bar above the table rather than inside the table's card. And its detail sheet has two parts: **journey flow cards** — one solid coloured card per stage (supplier, cargo, each stop, arrived here) joined by arrows, scrolling sideways for a long route — over a **package tracking table**, which is one row read left to right, with a coloured group header per stage and Received / Sent on / Still there beneath it. So the whole journey is one line across the screen, which is how the people using it think about it, rather than a stage per row. New `TruckIcon`. The stop picker is a `Select`, not a native `<datalist>` — the OS draws that one and it ignores the theme, as the customer-name field already proved.

Three things. **A stage was invisible**: the stops' cards and their table header used `bg-brand/80`, and the brand colour is a bare CSS variable with no alpha channel, so Tailwind could not build a value from the opacity modifier and rendered nothing — white text on white, and the Yangon stop simply vanished from both the journey and the table. Fixed properly rather than patched: four new `journey` CSS variables (`supplier`, `cargo`, `stop`, `final`) in `globals.css`, solid colours rather than opacity steps of one hue, so no two stages can ever read as the same block. They are applied as `style={{ backgroundColor: 'var(--color-journey-…)' }}` rather than through generated Tailwind utilities, and deliberately so: a colour added to `tailwind.config.ts` only reaches the screen once Tailwind rebuilds its utility set, and a dev server already running when the config changed goes on serving a stylesheet without them — which is how every journey card came out invisible a second time, after the first fix looked correct in a production build. Reading the variable directly has nothing to generate. **The last stage is "Final received", not "Arrived here"** — the business's own term, now used on the flow card, the table's group header and the list column. **The list page went back to the shared frame** — header row and filter strip inside the table's own panel, exactly as Customer Orders and Supplier Vouchers do it; the separate search bar the prototype uses made this one screen the odd one out. The tracking table also gained the prototype's borderless arrow columns between stages, a tick beside a stage holding nothing, and typed figures at the same weight as the printed ones.
- 2026-09-12 — Receiving Gate built, the wholesale workflow's fourth screen, and the one that keeps two jobs apart because they happen at different moments. **Step 1, at the roadside:** how many packages came off the truck and what the carrier charged — nothing else, because that is all anyone can honestly record while a truck waits. **Step 2, once the boxes are opened:** each package counted into its own row on the arrival's page — stock code, colours, sets, and a note for anything wrong with it. A package stays "Shut" until someone marks it opened, and its cells cannot be typed into before that, so nothing can be counted into a box nobody has looked inside. The check the page exists for sits above that table: the sets counted against the sets the supplier's voucher says are coming, staying quiet while boxes are still shut (a shortfall halfway through only means the rest are unopened), then turning green on a match or red on a difference — "2 sets short. The voucher says 25 sets are coming and 23 were counted." Status follows the same arithmetic rather than being stored: not opened → counting → all counted, or does not match. Changing the package count resizes the rows with it, trimming from the end and leaving anything already counted alone. Same frame as the other three screens (figure cards, one panel, gridline table, ⋮ actions column with a second delete confirm), so nothing new has to be learned to use it.
- 2026-09-12 — one naming convention across the four wholesale screens. Four files had drifted into saying the same thing different ways, which is how the screens themselves kept drifting. References settled on the word the screens use — `order_no`, `voucher_no`, `shipment_no`, `receiving_no`, no more `_number` beside `_no`. Dates took their label's name: `shipped_date` → `sent_date`, `arrival_date` → `received_date`. The receiving screen's expected quantities became `total_packages` and `total_sets`, matching both their own labels and the shipment's identically-named fields, instead of `packages_expected`/`expected_sets`. And the whole Arrival vocabulary became Receiving, since the nav item, the page, the reference prefix and the business all say receiving: `arrivals.ts` → `receivings.ts`, `ReceivingGatePage.tsx` → `ReceivingPage.tsx`, `Arrival`/`ArrivalPackage`/`ArrivalItem`/`ArrivalCost`/`ArrivalStatus` → `Receiving*`, `SEED_ARRIVALS` → `SEED_RECEIVINGS`. Nothing changed on screen except the one status spelling ("Partially received" → "Partly received", matching Supplier Vouchers); this pass was about the code saying what the screen says.
- 2026-09-12 — the four wholesale screens stopped being four copies of each other. Eleven components and four constants existed once per page — Panel, SectionLabel, FigureCard, RowProgress, StepBar, ReviewFact, ReadOnlyField, MenuItem, SuggestInput, CellInput, CountField, plus `PAGE_SIZE`/`EDITABLE`/`SOFT_BLUE`/`SOFT_RED` — which is precisely why they kept drifting: a fix to one never reached the others, and three of the eleven had already diverged into different versions. They now live once in `wholesale/ui.tsx`, about 930 lines lighter across the four pages. `StepBar` takes its steps as a prop rather than reading a local constant, and `RowProgress` takes its own label; `StatusPill` gives every badge one shape while each screen keeps its own words and colours. In the same pass the lists were cut from 13/14/15/16 columns to 9–11: the figures that came out are the ones the detail sheet already shows properly — a received figure that is only ordered minus remaining, progress bars, order and voucher totals, the journey's own package counts, and the receiving screen's costs. What stays is what a person scanning the list acts on.
- 2026-09-12 — there is now one journey, not three drawings of it. Delivery drew coloured cards from the shipment's real figures; Customer Orders and Supplier Vouchers each drew their own derived version — chips with a dot, guessed from a status — so the same goods moving looked like three different things. `DeliveryJourney` in `wholesale/journey.tsx` draws it once from the shipment itself, and the other two screens pass cards to hang on either end: a voucher adds **Voucher taken** in front, an order adds **Order created** in front and **Delivered to customer** at the end. The middle cards are then identical everywhere — same colours, same package counts, same ticks — because they are the same component reading the same data. The stage pieces (`JourneyCard`/`JourneyRow`/`JourneyArrow` and the four stage colours) sit in `ui.tsx`. Two honest gaps are shown rather than papered over: a voucher with no shipment raised yet shows only its own card and says so, and an order finds its shipment through the supplier and stock code on its first line, because a customer order does not name a voucher until allocation is built at the gate.
- 2026-09-12 — Inventory built, the piece between the gate and the customer. A receiving is an event — one truck, one day, never changed again — so no receiving screen can answer "how many black A1001 do we have?"; that is three receivings added up, less what has gone out. This screen is that sum: one line per stock code per place, counted in **sets**, because sets are what the gate counts and no pairs-per-set figure exists yet to convert them honestly. Stock moves **the moment a package is opened at the gate** rather than when somebody presses a button to release it — the pairs are physically there once the box has been looked in, a release step is one more thing to forget, and this business's packages arrive days apart, so anything that waits for a complete delivery would leave goods stranded and invisible. So what comes in is never typed here: `incomingMovements()` reads it off the receivings, and only what leaves is recorded on this page (to a customer order, or to another place), capped at what is actually held. The detail sheet shows every movement in and out with its reference, ending in "In stock now". New `stock.ts`; the page reuses the shared wholesale UI throughout.
- 2026-09-12 — delivering stock moved to the front of the Inventory page. It had been buried inside a stock line: to give a customer their pairs you opened the product, read a table inside it, and pressed a button there — and to know which product to open in the first place you went to Customer Orders and came back. Inventory now has two tabs. **Stock** is the table as it was, what is held and where. **To deliver** is the day's work as one flat list — a row per product a customer is still waiting for, with where it is, how much is in stock, who wants it, their address, the colors that order asked for, and how much of *that product* is still owed. Pressing Deliver opens the boxes in the table under that row, typed in the table's own cells. Nobody picks a product first: the question staff actually start from is "what do we owe today", and that is now the list they work down. The stock line's own page keeps the movement history and nothing else. Underneath, a customer order line gained its own `received_qty`, because "how much is still owed" is a question about a product on an order, not about the order as a whole — an order for two stock codes is rarely filled in one go, and the order-level figure could not say which half had gone.
- 2026-09-12 — one unit rule for the whole wholesale side, ending a confusion the screens had been carrying. A pair is the thing itself, **a set is 6 pairs and a dozen is 12**, and that conversion now lives in exactly one file (`wholesale/units.ts`). Every quantity is **stored in pairs**, whatever unit it was typed in, so no two screens can mean different things by the same number: a gate counting boxes in sets and a customer ordering in pairs are the same pairs underneath, and "10 pairs still owed" can finally be set beside "15 sets in stock" without either being a lie. What changed in the data: a receiving's package items carry `qty` **and** `unit` rather than a bare `sets`, its expected figure carries `total_qty` + `total_unit`, and stock movements carry `pairs`. What changed on screen: each product row at the gate has its own unit picker (a box of dozens says so), the gate's check compares in pairs but speaks in the receiving's own unit, and Inventory has a **Pairs / Sets / Dozens** switcher that re-reads every figure on the page — including the box you type a delivery into, so a delivery entered in dozens is stored as pairs without anyone doing arithmetic. Everything **reads in sets**, since that is how this business trades — customers order in sets, boxes are packed in sets — while pairs stay the figure underneath. Every seeded quantity was reset to a whole number of sets so nothing shows as "13.33 sets"; a figure that is not a whole set still displays honestly rather than being rounded away.
- 2026-09-12 — The colour shorthand now requires a unit letter on every colour: `black10s,pink2p,white1d` (s sets, p pairs, d dozens). The letter used to be optional, with a bare `black10` taking the row's unit, and that was the one place a figure could be read two ways — ten sets entered as ten pairs is a sixfold error that nothing downstream can catch. `colorQtyProblem` in `wholesale/shared.ts` now rejects a colour with no letter ("\"black10\" needs a unit — s for sets, p for pairs, d for dozens.") alongside the checks it already made for a missing count, a missing colour and an unknown letter, so the wizards on Customer Orders and Supplier Vouchers, the package items on Receiving and the delivery row on Inventory all block a save until every colour says what it is counted in. Placeholders and hints say so too. The seed data was rewritten to carry letters, and the stock screen's colour totals are now summed in pairs and written back with a letter — whole sets as `s`, anything that does not divide evenly as `p` — so what the system prints is in the same format it asks people to type.
- 2026-09-12 — A destination on a shipment's journey is finished only when nothing is still owed to it. `legRemaining` used to be that stop's own received less sent, so a stop that took in 7 of the 10 sent to it and forwarded all 7 read as 0 remaining with the green "Everything sent on" tick, hiding the 3 lost between the two places — the one thing the screen exists to show. It now takes what the place before it sent, less what it sent on, the same rule the gate at the end already follows, and the done tick needs something to have been sent toward the stop before it can turn green. Both the journey cards and the destinations table read the same figure.
- 2026-09-12 — Quantity and its unit are now one control, `QuantityInput` (and `QuantityField` for a figure already held as a number) in `wholesale/ui.tsx`: the number on the left, the unit picker inside the same frame on the right, sharing one border and one focus ring. They were two fields side by side, which never lined up — the number carried a hint underneath and the picker did not, so the picker sat a line lower — and read as two unrelated things when a unit is really part of the figure: "50" means nothing until you know it is sets. It replaces every quantity-plus-`UnitSelect` pair on Delivery (detail and wizard), Receiving (detail, package items, wizard) and Inventory's delivery row; `UnitSelect` itself is gone, since nothing pairs a unit with a number by hand any more. A `compact` flag gives the table-cell height.
- 2026-09-12 — Every reference number and stock code now has a small copy button beside it (`CopyButton` in `wholesale/ui.tsx`, with a new `CopyIcon`). These are the strings people carry to a phone call, a chat message or the supplier's own paperwork, and retyping "RCV-260912-0001" by eye is where a wrong digit gets in. It sits inside the `Reference` cell in every list, on the "… no." fields in every detail panel (`ReadOnlyField copyable`), and beside stock codes in the Inventory lists and the product tables on Customer Orders and Supplier Vouchers. The icon stays visible rather than appearing on hover — an icon that only shows when the pointer is already on it is an icon nobody finds — and turns into a green tick for a moment after copying. Copying falls back to the hidden-textarea trick where `navigator.clipboard` is missing, since a packaged Electron renderer is served from file:// and is not a secure context.
- 2026-09-12 — A product is now more than a stock code. `wholesale/products.ts` holds what the business sells — stock code, description, and the group it belongs to (man, lady, child) — and every product line on every wholesale screen carries a description and a group beside its code: customer order lines, supplier voucher lines, the items inside a received package, and stock. "A1001" tells nobody which shoe is meant, and the group is the difference between "we are short of B2001" and "we are short of ladies' sandals". A new `ProductCell` shows the description with a quiet grey `GroupTag` beside it — grey because it is a label, not a status, and colour on these screens already means good or still-owed. The wizards take the stock code through a `SuggestInput` over the known codes, and picking a code we already sell fills its description and group in, so the same shoe is not written two slightly different ways on two screens; a code we have not sold before is typed in full. Receiving keeps description and group in one Product cell rather than two columns, since that table is already wide. Searching Customer Orders, Supplier Vouchers and Inventory now matches a description as well as a code.
- 2026-09-12 — The five wholesale screens now keep one set of books (`wholesale/store.ts`). Each page used to hold its own copy of the seed data, so the screens could not agree: delivering goods on Inventory left the customer order still owing them, counting a package at the gate left the supplier voucher saying nothing had arrived, and leaving a screen threw the work away. Two rules live in the store because they are what keeps the screens telling one story — handing goods to a customer credits that customer's order (capped at what the line still wants, and the order's status follows the goods), and counting at the gate is what a voucher means by received, with the packages recorded there being what the shipment means by finally received. Alongside it: a stock line is "allocated" only when every pair on it is spoken for, measured in pairs owed rather than by the existence of any open order; a delivery cannot exceed what the customer is still owed, not merely what is on the shelf; `ordersWaitingFor` lists only orders still owed *that* product; the receiving wizard carries a shipment's unit along with its figure (taking the number alone read a shipment counted in pairs as the same number of sets); and a product row with no colours can no longer be saved. The seed data was rebalanced so every figure traces to a movement: what a customer has received is exactly what left the shelf for them, and what a voucher has received is exactly what the gate counted.
- 2026-09-12 — Payments, editing, and correcting a delivery. Money taken is now kept payment by payment rather than as one "paid" figure: a deposit, something on collection, the rest — which is how it actually happens, and a single number nobody can date cannot answer "when did that come in?". `PaymentsTable` in `wholesale/ui.tsx` shows them and takes the next one, identically on Customer Orders and Supplier Vouchers, capped at what is still unpaid; paid-so-far, unpaid amount and the status pill are all sums of that table. Both detail screens are now editable in place like Delivery and Receiving already were — header fields, and product rows where the colours drive the quantity exactly as they do in the wizard, with add and remove; a line whose colours fall below what has already gone to the customer says so in red. Stock itself is not editable, because it is not typed: the movements table on a stock line lets a delivery be corrected or removed, and the customer's order re-reads itself from it, while an incoming row says to fix it in Receiving, since it is the gate's own count. The store grew a `settle` step that runs after every change and re-derives every worked-out figure — order receipts and status from the deliveries, order and voucher totals from their lines, voucher receipts and shipment arrivals from the gate — so no screen has to remember to keep another honest.
- 2026-09-18 — sign-in screen rebuilt as a native two-pane desktop window (`AuthScreen.tsx`): a brand panel + form panel filling the whole window edge to edge, no floating web-style card, plus the same draggable custom-title-bar strip `AppShell` already uses so the window can be moved before signing in too. Piloted a single purple-blue (`#6366f1` / hover `#4f46e5` / active `#4338ca`) on that screen first, then — at the business's request to stop retail and wholesale looking like two different products — rolled it out everywhere: `globals.css`'s `--color-brand`/`-hover`/`-active` are now this one hex in *both* light and dark mode (dark mode used to lighten the brand colour for contrast; this hex already reads clearly on a near-black surface, so that step was dropped), and `.workspace-wholesale`'s old blue re-point (brand, info, and the blue-tinted surface/border greys) was deleted outright — Wholesale now inherits every colour token from `:root` same as Retail, keeping only its `.border` thickness bump. `roleBadgeVariant` (`AppShell.tsx`) and `WORKSPACE_COLORS` (`App.tsx`) both changed their wholesale entry from `"info"` to `"brand"` to match — those two were already documented as meant to agree with each other, so leaving one on the old blue would have quietly broken that invariant. The Windows `titleBarOverlay` effect's wholesale-only light-blue branch was removed for the same reason. The Delivery journey tracker's own blue was deliberately left alone in this pass (a shipment's stage is state, not brand identity) — then folded in too, immediately after, at the business's follow-up request: `--color-journey-cargo`/`-stop` now read `var(--color-brand)`/`var(--color-brand-active)` instead of their own blue, so the journey cards and package-tracking table on Delivery pick up the same purple-blue automatically and stay in sync if the brand colour ever changes again. `--color-journey-supplier` (neutral slate) and `--color-journey-final` (the app's own "success" green) are untouched, since those two were never the Wholesale blue in the first place.
- 2026-09-18 — semantic success/warning/error nudged toward the same purple-blue, at the business's request for the palette to feel like one coordinated family rather than clashing primaries next to the new brand colour. Each of `--color-success`/`-warning`/`-error` in `globals.css` is now a 90/10 blend toward `#6366f1` (`#18b18c`, `#e69822`, `#e14755`) — enough to read as "the same coloured world as the rest of the app" without losing green/amber/red as the thing being said; a heavier blend was tried and rejected in reasoning here (not applied) because red drifted toward magenta and stopped reading as urgent. The `-subtle` tint backgrounds were left alone: blending brand into amber's subtle tint (which carries almost no blue to begin with) turned the warning chip a muddy grey rather than a softer yellow, so `warning-subtle` and its siblings keep their original pale tints under the newly-blended text colour. Both light and dark mode pick this up automatically, since these three tokens were already defined once in `:root` with no separate dark override.
