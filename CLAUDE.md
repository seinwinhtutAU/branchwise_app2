# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Electron + React desktop app (frontend) with a FastAPI + Python backend, used by a Myanmar retail business ("branchwise") with one wholesale and three retail branches. Auth is **Neon Auth** (managed Better Auth, proxied through this project's own backend) and the app database is Postgres on **Neon** — it was moved off Supabase on 2026-09-05 because the free plan's egress allowance was the binding limit (the whole database is only ~28 MB). Supabase is gone entirely: its project was shut down on 2026-09-07, so logins moved too — see `docs/auth-and-accounts.md` for how sign-in now works and why the backend sits in the middle. Core features: cleaning messy POS report exports (sales/inventory/purchases, in Zawgyi-mixed Myanmar text) into structured data and persisting it (retail/admin); and a data-quality "Warning" page that surfaces numeric/missing-record/reconciliation issues found in the imported retail data.

This file is a quick-reference summary. For depth, read `docs/` — it's not auto-loaded, so check it deliberately when a task touches its area: `docs/architecture.md` (system overview), `docs/database-schema.md` (every table/column/relationship), `docs/retail/data-import.md` (the CSV cleaning pipeline, Zawgyi handling, branch resolution), `docs/auth-and-accounts.md` (Neon Auth, the backend-proxied login flow, and the seeded accounts), `docs/known-limitations.md` (deliberately-deferred gaps — check this before assuming something is a bug), `docs/retail/dashboard.md` (the per-branch Revenue/Cost/Inventory/Customer dashboard — every tab's endpoint, what each number means, and how it's computed), `docs/retail/branch_health.md` (the Overview tab's Branch Health Score, Early Warning alerts, and the exact arithmetic behind each alert's "why" — the weight/band table, the rule table, the revenue/margin/stock decompositions, the admin-tunable weights and thresholds, the "unmeasured is null, never 0" rule, and why all of it reuses the four pillars' and the Warning page's own logic rather than recomputing anything), `docs/retail/branch_health.md` also covers the "Business Alerts" nav page, which lists those same alerts for every retail branch at once, minus the data-quality ones; `docs/retail/business-alerts.md` is the plain-language companion to it — every alert condition, its exact firing threshold, and a worked numeric example per rule, written to be read by the business owner rather than by a developer. `docs/retail/import_health.md` (the "Import Health" tab, under the "Import Overview" nav item alongside "Import freshness", that checks whether import cleaning/confirm behaved correctly across Sales/Inventory/Purchase, separate from Warning). `docs/retail/checking.md` (the "Physical Stock Audit" screen — reuses the Warning page's own missing-product/reconciliation checks to tell staff exactly what to recount; fully built but deliberately hidden from the nav for now).

Wholesale is documented in full under `docs/wholesale/` — `docs/wholesale/README.md` is the entry point (shared conventions: pairs/colours/money/reference-numbering/audit/lifecycle), with one doc per screen (`shipments.md`, `receiving.md`, `supplier-vouchers.md`, `customer-orders.md`, `inventory.md`, `finance.md`, `monitoring.md`, `master-data.md`, `write-offs.md`).

## Commands

### Frontend / orchestration (run from repo root)

```
npm install
npm run dev:all          # Electron+Vite dev server AND the FastAPI backend together (recommended)
npm run dev               # Electron+Vite only
npm run backend:dev       # FastAPI only (uv run --directory backend uvicorn app.main:app --reload --port 8000)
npm run typecheck         # tsc for both the main/preload (node) and renderer (web) tsconfig projects
npm run lint
npm run format
npm run build             # typecheck + electron-vite build
npm run build:mac / build:win / build:linux
```

### Backend (Python, managed with `uv`)

**Always run backend commands with `uv run --directory backend ...`** (or `cd backend` first) — not `uv run --project backend ...` from the repo root. `--project` only locates the venv/pyproject; it does not change the working directory, and `app/config.py`'s `Settings` loads `.env` via a relative path, so running from the repo root silently loads the _root_ `.env` (the frontend's Vite vars) instead of `backend/.env`, and `DATABASE_URL`/`NEON_AUTH_BASE_URL` end up empty. This has bitten this project's own dev workflow before (see `package.json`'s `backend:dev` script, which uses `--directory backend`).

Exception: the one-off scripts in `backend/scripts/` (see below) don't touch `app.config`/the database at all, so they're fine to run with `--project backend` from the repo root.

```
uv sync --project backend                                   # install/update deps (creates backend/.venv)

uv run --directory backend pytest -q                        # all tests
uv run --directory backend pytest -q tests/test_pos_import.py                                    # one file
uv run --directory backend pytest -q tests/test_pos_import.py::test_zawgyi_description_converted_to_unicode   # one test

uv run --directory backend alembic revision --autogenerate -m "..."   # new migration (review before applying)
uv run --directory backend alembic upgrade head                       # apply migrations

# Clean a raw POS export without going through the app (writes retail_data/*_clean.csv by default):
uv run --project backend python backend/scripts/clean_sale_csv.py
uv run --project backend python backend/scripts/clean_inventory_csv.py
uv run --project backend python backend/scripts/clean_purchase_csv.py
```

Tests never touch the real database: `backend/tests/conftest.py`'s `client`/`db_session` fixtures override `get_db` with a fresh in-memory SQLite per test. This matters because `backend/.env`'s `DATABASE_URL` points at a real (Neon) Postgres instance — any test that exercises a DB-writing endpoint must go through these fixtures (`authed_client` also overrides `get_current_user` to skip real JWT/network verification).

## Architecture

### Two-language monorepo, one root `package.json`

`frontend/` (Electron main/preload/renderer, TypeScript) and `backend/` (FastAPI, Python/uv) are independent toolchains glued together by `npm run dev:all` (via `concurrently`). `electron.vite.config.ts` at the repo root points at `frontend/main`, `frontend/preload`, `frontend/renderer` explicitly (the electron-vite convention of `src/main` etc. doesn't apply here since the layout was renamed).

There are **two separate `.env` files** — don't confuse them: repo-root `.env` holds `VITE_*` vars for the Electron renderer (currently just the API base URL); `backend/.env` holds the FastAPI vars — `DATABASE_URL`, `PORT`, `NEON_AUTH_BASE_URL`/`NEON_AUTH_JWKS_URL`, `OPENAI_API_KEY`/`OPENAI_CHAT_MODEL` for the chatbot, and `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET` for the optional Cloudflare R2 storage of original import files (see `docs/retail/data-import.md`; unset means storage is silently skipped, not an error). See the `uv run --directory backend` note above for why mixing these up silently breaks things rather than erroring loudly.

### Backend: a shared core plus `retail/` and `wholesale/` packages

Retail (POS import/dashboard/warnings) and wholesale share the same Postgres database, the same Neon Auth login, and the same `branches`/`users` tables — but neither business's own data ever references the other's (a sale never points at a customer order, a shipment never points at a sale). `backend/app/` reflects that: `app/routers/`, `app/services/`, and `app/models/` hold only the handful of things both sides need (`auth.py`, `branches.py`, `health.py`, `settings.py`; the `Branch`/`User`/`AppSetting` models), and everything else lives in `app/retail/{routers,services,models}/` or `app/wholesale/{routers,services,models,schemas}/`. A file's package tells you which business owns it; nothing outside `app/retail/` imports from inside it, and likewise for `app/wholesale/`. `app/main.py` imports each domain's routers from its own package when wiring up `create_app()`.

### Frontend: the same split, one layer up from `wholesale/`

`frontend/renderer/src/components/features/` mirrors the backend boundary: `shell/` (`AppShell.tsx`, `AuthScreen.tsx`, `ConnectionBanner.tsx`) is the app chrome every screen sits inside; `chat/` and `settings/` are genuinely cross-business (`SettingsPage.tsx` has its own Wholesale tab; `settings/UserManagementPage.tsx` is the admin-only account CRUD screen, cross-business since an admin can create any role there — see `docs/auth-and-accounts.md`); retail's own pages live in `retail/` (`DashboardPage.tsx`, the import screens, `WarningsPage.tsx`, `BusinessAlertsPage.tsx`, retail's own `InventoryPage.tsx` — not to be confused with wholesale's). `wholesale/` itself is split the same way one level further down: `orders/`, `delivery/`, `receiving/`, `vouchers/`, `inventory/`, `masterData/`, `monitoring/`, and `finance/` each hold one screen's page, its data/API files, and its own components; `shared/` holds what several of them use (`ui.tsx`, `formFields.tsx`, `journeyVisuals.tsx`/`journey.tsx`, `paymentsTable.tsx`, `drawers.tsx`, `useDismissableMenu.ts`, `WriteOffModal.tsx`, `ColorQtyPicker.tsx`, `shared.ts`, `units.ts`, `currency.ts`, `products.ts`, `exportUtils.ts`, `store.ts`, and the `api.ts` barrel over `apiClient.ts` plus each screen's own `*Api.ts`). A handful of one-line files stay at `wholesale/`'s own top level (`CustomerOrdersPage.tsx`, `DeliveryPage.tsx`, `InventoryPage.tsx`, `ReceivingPage.tsx`, `SupplierVouchersPage.tsx`) purely as re-export shims, so `App.tsx`'s lazy-import paths didn't need to change when the real components moved into their subfolders. Two files stayed at the shared `features/` top level rather than moving into `retail/` despite looking retail-only at a glance: `dashboard/` (its `shared.tsx`/`helpers.ts`/`usePeriodRange.ts` are also imported by the wholesale Dashboard's Revenue/Customer/Inventory tabs (`wholesale/monitoring/`) for `StatTile`/`TrendChart`/`ChartViewToggle`/`formatCount`) and `types.ts` (its `Profile` type is imported almost everywhere, wholesale included, even though the same file's `ImportPreviewResult`/`RowIssue`/etc. are retail-only). `components/ui/` and `lib/` remain shared infrastructure for both.

### Auth: two layers, two "users"

Neon Auth (managed Better Auth) issues JWTs signed with EdDSA/Ed25519 — `app/core/security.py`'s `get_current_user` verifies them via Neon Auth's JWKS endpoint (`PyJWKClient`), not a static secret. `get_current_app_user` goes one step further: it loads the corresponding row from _our own_ `users` table (matched via a separate `auth_user_id` column, not a shared primary key — see `docs/auth-and-accounts.md` for why) to get app-level profile data (`role`, `branch_id`, `name`). A Neon-Auth-authenticated user isn't fully onboarded until both exist — the app's own self-service Sign Up form still only creates the Neon Auth side, with no `users` row until one is created separately. That separate step no longer requires a script: admin and development accounts can provision an account (auth + `users` row together); only development can assign the `development` role.

`GET /api/me` returns the full app-level profile (via `get_current_app_user`), not just raw JWT claims.

Five roles exist: `development`, `admin`, `retail_management`, `wholesale`, `retail`. `development` has the full cross-workspace system access and can assign every role. `admin` has the same system access, except it cannot assign or manage a `development` account. `retail_management` has full retail operational access, every retail branch, and no fixed `branch_id`, but no Wholesale workspace or account management. `require_advanced_dashboard` gates the Revenue/Cost/Inventory/Customer dashboard tabs to every retail role (`development`/`admin`/`retail_management`/`retail`) except `wholesale`.

### The CSV/XLS/XLSX import pipeline

POS exports (`retail_data/{sale,inventory,purchase}.csv`) are printed-report formats, not clean tables — metadata lines, multi-row headers, repeating slip blocks (sales), grand-total/footer rows. Each of `app/retail/services/{pos,inventory,purchase}_import.py` parses one export type by **structurally classifying rows** (does this row have a numeric quantity/price in the expected position? does it start with a known label like "Total"?) rather than assuming fixed line numbers, so the same parser keeps working across different files of the same format. Shared, format-agnostic logic lives in `app/retail/services/import_common.py`: reading csv/xls/xlsx into a raw grid, number parsing (strips thousands separators), and `clean_text`/`is_zawgyi`.

**Zawgyi**: Myanmar retail data is a mix of legacy Zawgyi-encoded text and standard Unicode — both use the same Unicode code points but order them differently, so a file can contain _both_ correctly-encoded and Zawgyi-encoded Myanmar text side by side. `clean_text` only runs the Zawgyi→Unicode converter (`pyidaungsu.cvt2uni`) when `is_zawgyi` actually detects Zawgyi encoding — blindly converting corrupts already-correct text. `is_zawgyi` calls `pyidaungsu`'s underlying fasttext model directly (`pds.f.f.predict`) rather than its public `detect()`/`predict()` wrapper, which crashes under the numpy version this project uses.

Each import type has a matching pair of endpoints in `app/retail/routers/imports.py`: `POST /api/imports/{type}` (parse + preview only, returns both the raw grid and the cleaned rows, nothing persisted) and `POST /api/imports/{type}/confirm` (re-parses the same upload and persists via `app/retail/services/{sales,inventory,purchase}_persist.py`). Confirm endpoints resolve which branch the data belongs to from the uploader's own `users.branch_id`; an account with no branch (e.g. admin) must supply one explicitly via a `branch_id` form field, and the server ignores any client-supplied `branch_id` for accounts that already have one. Purchase confirm also accepts optional `purchase_date` (`YYYY-MM-DD`) and `purchase_number` form fields, both falling back to values extracted from the filename (`extract_purchase_metadata`) when omitted.

There's also a lighter `POST /api/imports/inspect` (type/date/purchase-number/row-count check without building the full preview grid) behind the main Import Hub's bulk multi-file flow (`ImportConfirmModal.tsx`: pick several files, inspect each, confirm the valid ones straight through) — the original single-file full-grid preview/confirm still exists and is used by Import History's "Reimport" and the Warning page's "Import to fix" (`ImportReviewPage.tsx`). See `docs/retail/data-import.md` for the full picture, including how the two flows differ and why. Every confirm also uploads the original file to Cloudflare R2 when configured (`app/services/storage.py`; see the `.env` note above) — `import_batches.storage_key` records it, and admin can download it back via `GET /api/imports/history/{id}/download`.

Product descriptions are title-cased on import (`import_common.clean_description` — "golden duck" → "Golden Duck"), leaving Myanmar text and digit-carrying words like "500ML" alone; `backend/scripts/titlecase_product_descriptions.py` (dry run by default, `--apply` to save) does the same to rows imported before that rule. See `docs/retail/data-import.md`.

Products (`app/retail/models/product.py`) are shared/deduplicated across all three import types, upserted by the natural key `stock_code` via `import_common.get_or_create_products` — a single batched `SELECT ... IN (...)` plus in-memory create/update, not a per-row round trip. This matters at scale: a naive per-row version of this against the remote Postgres pooler took minutes on a 900-row inventory file and hit request timeouts; batched, the same file imports in ~5s. All the ORM models use client-generated UUID primary keys (`id=str(uuid.uuid4())` set explicitly in the persist services, not left to the SQLAlchemy column `default`) specifically so child rows can reference a parent's `id` before any flush.

Sales import is idempotent per slip (`sales.slip_id` is unique; re-confirming the same file skips already-imported slips). Purchase import is **not** idempotent — `purchase.csv` has no natural per-batch key in the source data, so every confirm creates a new `Purchase` batch; re-uploading the same file double-counts. `stock_levels` (inventory) intentionally keeps full history — every confirmed import adds new snapshot rows rather than overwriting, and "current stock" is the set of rows carrying a branch's newest `snapshot_at` — one whole count, not the newest row per product (see `app/retail/services/stock.py`).

Every confirmed import also creates one `ImportBatch` row (`app/retail/models/import_batch.py`), and every `Sale`/`Purchase`/`StockLevel` it creates links back to it via `import_batch_id`. `GET /api/imports/history` lists these (same own-branch-or-admin visibility rule as confirm); `POST /api/imports/history/{id}/revert` deletes the batch's data rows but keeps the `ImportBatch` itself marked `reverted` (or `reimported`, when the revert's `?replaced=true` flag says a corrected file is about to replace it — same effect on the data, just a different audit label) — an audit trail, not a silent erase. This is also the mechanism for fixing a wrong import: revert it, then just confirm the corrected file again through the normal flow.

### Database models

SQLAlchemy 2.0 style (`Mapped`/`mapped_column`), one file per entity, registered in `app/models/__init__.py` (required for Alembic autogenerate to see them) regardless of which package a model actually lives in — `app/models/` for the shared `Branch`/`User`/`AppSetting`, `app/retail/models/` for `Product`/`Sale`/`Purchase`/`StockLevel`/`ImportBatch`, `app/wholesale/models/` for `entities.py` (`Shipment`, `CustomerOrder`, `Receiving`, `SupplierVoucher`, ...) and `master_data.py`. `Branch`/`User` are the base entities (`users.branch_id` nullable — not every role has a branch). `Product` is shared across `SaleLine`, `PurchaseLine`, and `StockLevel` — the retail import pipeline's shared product catalog, keyed by POS `stock_code`. Money/quantity columns use `Numeric`, not `Float`. `alembic/env.py` reads the DB URL from `app.config.get_settings()` at migration time rather than from `alembic.ini`. A Postgres enum column (`User.role`, `ImportBatch.status`, ...) can't gain a new value through a normal autogenerated migration — adding `retail_management` needed a hand-written `ALTER TYPE userrole ADD VALUE` migration instead (`20260921_add_retail_management_role.py`).

### Wholesale: rebuilt screen by screen, source-first

The old wholesale workflow (customer orders and factory vouchers, entered inline in the UI) **was deleted on 2026-09-11** — models, schemas, services, routers, tests, and all four renderer pages. `diagram/wholesale/erd.mmd` (plain-language companion: `diagram/wholesale/erd-notes.md`) sketched the replacement, but the five wholesale screens (Customer Orders, Supplier Vouchers, Delivery, Receiving, Inventory) were then built front-end only against `wholesale_prototype/`'s UI, and moved on from the ERD in real ways — quantities are stored in pairs (`WholesaleUnit`: 6 pairs = 1 set, 12 = 1 dozen), colours carry their own unit letter, and most "status"/"total" fields are worked out on read rather than stored. The backend now follows the screens, not the original diagram.

The backend is being wired in screen by screen, in **source-first** order — Delivery, Receiving, Supplier Vouchers, Customer Orders, then Inventory — rather than nav order, so each screen's derived figures (a voucher's received quantity, a shipment's finally-received packages) are already correct the day it ships instead of reading zero until a later phase supplies what they are derived from. Until a screen's phase lands it still reads from `frontend/renderer/src/components/features/wholesale/store.ts`, an in-memory `useSyncExternalStore` seeded from the front-end's own demo data; a screen whose phase has landed reads and writes `/api/wholesale/...` and pushes its rows into that same store via a `hydrate*` function, so screens still on the store keep seeing real data the moment a screen ahead of them has fetched it.

**Done:** Delivery (phase 1) — `wholesale_shipments`/`wholesale_shipment_legs` (`backend/app/wholesale/models/entities.py`), `/api/wholesale/shipments` (`backend/app/wholesale/routers/shipments.py`), business rules in `backend/app/wholesale/services/` (`colors.py`, `units.py`, `references.py`, `shipments.py` — the last porting `normaliseFlow` and friends from `frontend/.../wholesale/delivery/shipments.ts` line for line, since the server is now authoritative and the client copy is only instant feedback while typing). Seed data: `backend/scripts/seed_wholesale_demo.py` + `backend/scripts/data/wholesale_demo.json` (two months of simulated trading, generated by `backend/scripts/build_wholesale_demo_data.py`; `--wipe` replaces a branch's wholesale rows *and* the global wholesale master lists), idempotent without `--wipe`, run with `uv run --directory backend python scripts/seed_wholesale_demo.py --branch "Wholesale"`.

**Done:** Receiving (phase 2) — `wholesale_receivings`, packages, items and costs are created by migration `9f2a8c4d1e37`; `/api/wholesale/receivings` saves header details, package counts and staged costs. The Receiving page reads through the shared cache and keeps edits local until its Save button is pressed.

**Done:** Supplier Vouchers (phase 3) — migration `c3a7d9e2f641` creates vouchers, their colour-validated lines, and supplier payments. `/api/wholesale/supplier-vouchers` computes line totals, supplier balances and received pairs from the authoritative Receiving records; the Supplier Vouchers page now persists creation, edits, deletion and payments.

**Done:** Customer Orders and Inventory — Customer Orders persist headers, colour-validated lines, cancellation and customer payments; Inventory stores only outgoing customer deliveries in `wholesale_stock_movements` (migration `1d74e5f1b7c1`), computes incoming stock from opened Receiving packages, and Stock Records covers the whole wholesale pipeline: supplier vouchers, shipments, receivings, customer orders and deliveries, including products that have not arrived yet. A delivery is capped by both shelf stock and the customer's remaining order quantity, and the order's received quantity/status is recomputed from those rows. Wholesale list endpoints accept search/filter/page parameters and return `X-Total-Count`; the current UI remains compatible with the default 100-row page. The demo seed refuses to mix with existing wholesale data unless `--force` is given (or `--wipe` is intentionally requested). Allocating arrived stock to a customer order happens automatically the moment a receiving package is opened (`auto_allocate_arrivals`, oldest order first); the Allocate screen exists only to handle what that couldn't cover.

Beyond the five phases above, the wholesale workspace also has: **Finance** (`/api/wholesale/finance/customers` — receivables; supplier payables and shipment costs are read-only reuses of the Supplier Vouchers/Receivings list endpoints, not separate endpoints), **Master Data** (`app/wholesale/models/master_data.py` — the shared product catalog plus five simple reference lists: suppliers, customers, cargo companies, carriers, destinations, receiving gates; soft-delete only), and **Write-offs** (`wholesale_write_offs` — one polymorphic, append-only "explain the quantity mismatch" log shared by Shipments, Supplier Voucher lines, and Customer Order lines). **Monitoring** (the wholesale "Dashboard": Summary and Operations views, plus Revenue, Customer and Inventory tabs served by `GET /api/wholesale/dashboard/{revenue,customer,inventory}`, and buttons that export every wholesale table to Excel/CSV via `GET /api/wholesale/export` — see `docs/wholesale/monitoring.md`) is in the nav. There is no separate Reports page; it was removed in favour of those tabs.

Every wholesale router is gated by `app/wholesale/routers/common.py::require_wholesale` (allows `wholesale`/`admin`, mirroring `app/retail/routers/common.py::require_retail`'s allow-list on the other side). Every entity's "status" is computed on read from a `lifecycle.py` state machine, never stored — see `docs/wholesale/README.md` for the shared conventions (pairs/colours/money/reference-numbering/audit) every screen above uses, and `docs/wholesale/*.md` for each screen's full mechanics.

### Data-quality Warnings

`app/retail/services/data_quality.py` backs `GET /api/warnings`, read by the "Warning" nav page (any retail-workspace role — `require_retail`, see the Auth section above). It runs a set of independent checks over already-imported retail data — bad numeric values on sale/inventory/purchase rows (reusing each import type's own `VALIDATION_RULES`), stock codes sold/purchased but missing an inventory record, and a daily reconciliation check comparing the latest inventory snapshot against `previous snapshot + purchases − sales` since then. Each check returns rows with a plain-English note, the field(s) actually at fault, and (when traceable to one confirmed import) a link into Import History — reverting and re-confirming that batch is the fix for most of these. The reconciliation check is UOM-naive (no per-product unit-conversion table), so a mixed-unit product surfaces as a separate "verify by hand" warning rather than a false mismatch. The Sale/Purchase check window (default: today only) is user-configurable on the Settings page and passed as `?days=`.

Two performance rules matter here, because these checks are what the dashboard tabs spend most of their time on. First, each numeric check **validates a cheap projection of just the rule columns first and only then enriches the rows that failed** (point-in-time pricing, the source import batch) — enriching everything up front cost ~750ms per request whose entire output was thrown away on clean data. Second, `build_warning_sections` takes an optional `section_ids` set so a caller that displays one tile doesn't compute all six checks; the Cost dashboard used to run 1.5s of checks to show a 34ms one.

`GET /api/checking` (`app/retail/routers/checking.py`) reuses this same machinery (`build_checking_items`, filtered to the missing-product/reconciliation checks) to drive a "Physical Stock Audit" screen — the list of products staff need to verify by hand in the external inventory system, unlocked only after a configurable daily cutoff once today's sale and inventory files are both in. It's fully built but deliberately left out of the nav until the daily-check workflow it depends on is ready — see `docs/known-limitations.md`.

### Weak connections

The backend is local but the database (Neon) is not, so every screen depends on the internet. `docs/architecture.md`'s "Working on a weak connection" section covers what's in place: `pool_pre_ping`/`pool_recycle`/keepalives on the Postgres engine, a `window.fetch` wrapper (`lib/network.ts`) that times out and retries **reads only** — never writes, which may already have been applied — the page cache persisted to `localStorage` so a launch shows the last known numbers, and a connection banner driven by the app's own requests (not `navigator.onLine`, which is always true here) that polls `GET /api/health/db` while offline.

### Electron CSP

`frontend/renderer/index.html` sets a `Content-Security-Policy` meta tag with an explicit `connect-src` allowlist (currently just the local dev backend plus the deployed backend hosts). It needs no third-party entry any more — `https://*.supabase.co` came out of it when auth and the database both moved to Neon (see "What this is" above). Any new external endpoint the renderer needs to `fetch()` must still be added here, or the request fails silently with no network-level error surfaced — this has already caused a debugging session once in this project.

## Keeping the codebase maintainable

Left alone, a codebase this size drifts toward duplicated logic and oversized files simply from features being added one at a time. A few habits, all things this project has actually done rather than aspirations, keep it from doing that.

**Extract duplicated logic once it's proven duplicated, not on the first occurrence.** The signal is two or three near-identical copies of the same non-trivial logic — a dropdown's open/confirm/dismiss behaviour, a keyboard shortcut's key-matching, a state machine's shape — usually with small, uncoordinated drift already appearing between the copies, which is worse than the duplication itself: a bug fix to one copy silently never reaches the others. `useDismissableMenu` and `DotPill`/`StatusPill` (`frontend/.../wholesale/shared/ui.tsx`) and `useSearchShortcut` (`frontend/renderer/src/lib/`) all exist because that had already happened across 3+ files. A single occurrence, or two copies that are only superficially similar, is left alone — extracting on the first write is premature abstraction, not maintainability.

**Split a file or folder once it's grown past a few hundred lines, or past a dozen-odd files at one level, along its own natural seams** — one file or folder per screen/domain, plus a `shared/` for whatever more than one of them actually uses. `backend/app/{retail,wholesale}/` and `frontend/.../wholesale/{orders,delivery,receiving,...,shared}/` are both this same move. The part that matters more than the split itself: **check what actually imports a file before deciding it's domain-specific — don't guess.** `dashboard/` and `features/types.ts` both looked retail-only until `grep -rl` turned up wholesale screens importing from them too (the wholesale Dashboard's tabs use `dashboard/shared.tsx`'s `StatTile`; `types.ts`'s `Profile` is imported almost everywhere). A "clean" reorganization based on what a file *looks like* it's for, rather than who actually imports it, quietly breaks an unrelated screen.

**Split a widely-imported file without updating every caller** by turning the old file into a thin barrel (`export * from "./newLocation"`) instead — see `wholesale/api.ts` (a 14-line barrel over 8 domain files) and `wholesale/ui.tsx` (keeps the primitives, re-exports the rest). Once something lives inside a folder already named after its domain, the redundant prefix comes off on the way in (`wholesale_orders.py` → `wholesale/routers/orders.py`), since the folder now says what the prefix used to.

**Verify a reorganization mechanically, not by re-reading the diff.** Run the full test suite, `typecheck`, and lint after every batch of moves, and diff the sorted list of exported names before and after a split (`grep -oE "^export ..." old.ts | sort` against the same over every new file) to catch a name that got dropped or silently duplicated — this caught real mistakes during the wholesale/backend split. Two footguns worth remembering before scripting a bulk rename with `sed`: macOS's built-in `sed` doesn't support `\b` word-boundary regex — a rule using it silently matches nothing, so test the pattern against a throwaway string before trusting a big rewrite to it — and if a destination folder's name equals one of the source names being moved into it (e.g. a file called `masterData.ts` moving into a new `masterData/` folder), an ordered list of replacement rules can re-match its own already-rewritten output and double the path up (`masterData/masterData/MasterDataPage`); grep the result for that pattern before moving on.
