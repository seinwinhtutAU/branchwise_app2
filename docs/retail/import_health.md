# Import Health

**Status: implemented.** The retail **Import Health** tab is rendered by `frontend/renderer/src/components/features/retail/ImportHealthPage.tsx`. It combines the existing `GET /api/imports/freshness` and `GET /api/imports/completeness` responses in the frontend; no backend response shape is changed. The tab remains available from the Import Hub for non-retail roles.

## Why this exists

On 2026-08-30, a real bug was found and fixed: `sales.slip_id` (built from just report date + slip number, see `app/retail/services/pos_import.py`) was globally unique instead of scoped per branch, even though different branches/POS terminals number their own slips independently. The result — 1,356 real sales (AungThitSar's Feb 2026 import, mostly) were silently skipped as "already imported" and never persisted, with no error anywhere. It was only found by writing a one-off audit script against the real database, because nothing in the app itself would ever have surfaced it. Import Health is the standing feature that replaces that one-off script: it should have caught this the day it happened.

It is a different concern from what already exists:

- **Import History** shows what a past import batch did, after the fact, one row at a time.
- **Warning** (`app/retail/services/data_quality.py`) checks data that's already been saved for numeric/reconciliation issues.
- **Import Health** checks whether the _cleaning and confirm step itself_ behaved correctly, at the moment it matters — before a bad import quietly rots for months.

This covers all three import types (Sales, Inventory, Purchase), not just Sales. The 2026-08-30 incident happened to be a Sales bug, but each import type has its own way of silently going wrong at confirm time (see "Batches to review" below). Slip-total mismatches are Sales-specific by nature (only Sales' source format has a slip subtotal row), not because the feature is scoped to Sales.

## Combining freshness and completeness

The Import Hub exposes one **Import Health** view rather than separate stacked tables. The frontend requests `GET /api/imports/freshness` and `GET /api/imports/completeness` together, then merges rows by `branch_id`. This keeps the existing branch visibility rules and lets the UI present the operational picture in one place: freshness tells the user when data last arrived, while completeness tells them which daily dates still need attention.

One shared Refresh button reloads both endpoints. Ignore/restore actions still use the existing completeness close/reopen endpoints; after an action, the affected branch card is refreshed without changing the backend contract.

## Sections

### 1. Upload and data freshness — implemented

Per retail branch, the page shows the latest confirmation time and also verifies what date the file actually contains. Sale uses the newest `sales.sale_date`; Inventory uses the newest `stock_levels.snapshot_at` date. The daily badge grades those data dates, so confirming yesterday's report today remains visibly stale rather than reading as a fresh upload. Purchase is not graded as late because it is not daily; instead, its numeric purchase numbers are grouped by prefix and checked for internal gaps (for example, `STR00049` followed by `STR00111` flags `STR00050`–`STR00110`). The same two checks surface as critical Business Alerts and link back here.

**Sales and Inventory are graded as daily** — Today (success), Yesterday (warning, maybe just not uploaded yet today), "N days ago" or "Never imported" (error). **Purchase is not.** The business only buys stock when it restocks, not every day, so a purchase import that is a week old means "nothing was bought that week," not "someone stopped uploading" — grading it daily made a normal branch look permanently red. Its cell shows the same "N days ago"/"None yet" wording in a neutral badge, and the column header is marked "(not daily)" so the missing color isn't read as a bug. No longer threshold was substituted, because any number would be arbitrary: purchasing frequency isn't fixed, and this table has no way to know when a branch _should_ have restocked.

### 2. Batches to review — implemented (all three import types, each with its own check)

**Endpoint**: `GET /api/imports/health?days=7|30|90` (default 30) — same branch-visibility rule as everything else in `imports.py` (an admin sees every branch, a branch-scoped account sees only its own; no `branch_id` picker, since the whole point is one shared list rather than viewing one branch at a time). Only `COMPLETED` batches are considered — a `REVERTED`/`REIMPORTED` batch's issue is already resolved.

One shared table (`batches_to_review` in the response), but what makes a batch "flagged" differs per import type — `app/retail/services/import_health.py`:

- **Sales** (`sales_skip_rate_reviews`) — flags a batch whose skip rate (`sales_skipped_duplicate / (sales_created + sales_skipped_duplicate)`, both already in `ImportBatch.summary`, no new query needed) is ≥ `SALES_SKIP_RATE_THRESHOLD` (15%) _and_ the skipped count is ≥ `SALES_SKIP_MIN_COUNT` (5, so a tiny file like 1-of-6 skipped doesn't flag on noise alone). A flat threshold was chosen over a per-branch rolling baseline — real skip rates in this dataset cluster at 0-4% on a normal re-upload, and the incident that motivated this feature was 41%, so a flat 15% cleanly separates the two without needing history to compare against. Revisit if real data ever produces a false positive/negative at this threshold. Excludes any batch whose filename starts with `RECOVERY_REPLAY_FILENAME_PREFIX` (`"[recovery replay] "`) — a manual data-recovery replay is _supposed_ to skip most of its rows (correctly avoiding re-creating what's already there), so flagging one is a false positive, not a signal.
- **Purchase** (`purchase_duplicate_reviews`) — Purchase has no dedup at all (`purchase.csv` has no natural batch key — see `docs/retail/data-import.md`), so the risk is the opposite of Sales: a re-upload silently double-counts spend instead of being silently skipped (a known, previously-documented gap — `docs/retail/dashboard.md`'s Cost tab). Flags a batch confirmed in the requested window whose total (`sum(PurchaseLine.quantity * PurchaseLine.buying_price)` for that batch) is within `PURCHASE_DUPLICATE_AMOUNT_TOLERANCE_PCT` (2%) of another completed batch for the _same branch_ within a `PURCHASE_DUPLICATE_LOOKBACK_DAYS` (60-day) window. Deliberately simpler than the original design note's "overlapping product set" idea — matching totals alone was enough to be a useful, cheap signal at this business's scale, and product-set overlap can be added later if totals alone prove too noisy in practice.
- **Inventory** (`inventory_anomaly_reviews`) — keeps full snapshot history by design, so a repeat upload isn't wrong on its own; the failure mode is a bad/partial parse. Flags a batch whose distinct-`stock_code` count is below `INVENTORY_ANOMALY_RATIO` (50%) of the median count across that branch's last `INVENTORY_BASELINE_LOOKBACK_BATCHES` (10) completed Inventory batches — but only once at least `INVENTORY_BASELINE_MIN_BATCHES` (3) prior batches exist, so a branch's first few imports aren't compared against nothing. The original design note's "on-hand quantity jump" idea was left out of this pass — product-count anomaly alone already covers the "file got cut off" failure mode directly, and quantity-based anomaly detection would need its own tuning pass against real data before it's worth the complexity.

### 3. Slip-total mismatches — implemented (Sales only)

`app/retail/services/pos_import.py`'s `parse_pos_sale_export_from_grid` already compared each slip's line-item total against its own printed subtotal row and only ever logged the mismatch (`logger.warning`, never reaching a user). It now also appends each mismatch to `df.attrs["subtotal_mismatches"]` (same mechanism as the existing `origin_indices` attr), which `confirm_sales_file` (`app/retail/routers/imports.py`) reads straight off the parsed DataFrame and passes into `persist_sales`, which stores it as `slip_subtotal_mismatches` on the batch's own `summary` JSON — so it rides along with every confirm, no separate persistence needed. `import_health.slip_total_mismatches` just reads that key back out of each Sales batch's `summary` within the requested window. Batches confirmed before this change simply have no `slip_subtotal_mismatches` key and are skipped (`.get(..., [])`), not an error.

### 4. Dismissing a flagged batch — implemented

A batch's flag comes from `ImportBatch.summary`, a frozen snapshot from confirm time — so a batch confirmed while a bug was live (like the 2026-08-30 incident) keeps showing as flagged forever, even after its data gap was patched by a separate later batch, since nothing links the two. Rather than try to _infer_ "already resolved" (unreliable), `ImportBatch` gained two nullable columns, `health_dismissed_at`/`health_dismissed_by` (migration `617428f4df12`), set via `POST /api/imports/health/{batch_id}/dismiss` (`undismiss` to reverse) — same branch-visibility rule as everything else (`_can_access_batch`: admin any batch, everyone else only their own branch's, 404 otherwise). Dismissing only hides a batch from `batches_to_review`'s Sales/Purchase checks going forward (`_branch_scoped_batches` and `purchase_duplicate_reviews` both filter `health_dismissed_at.is_(None)`); it never touches the batch's data, `status`, or its place in Import History — a dismissed Inventory anomaly's product count still counts toward other batches' baseline calculation, since dismissal means "don't re-flag this," not "this batch didn't happen." The frontend's "Dismiss" link sits next to "View in History →" on every `batches_to_review` row.

## Frontend

`frontend/renderer/src/components/features/retail/ImportHealthPage.tsx` renders one card per branch. The header shows the branch name, a status badge ("Up to date", or "Review ignored days" when only ignored days remain) and an `N ignored` link. A **Data range** block lists the earliest–latest date held for Sales, Inventory and Purchase, then each open issue is one row with a category tag, plain text ("3 missing sales days", "2 missing purchase numbers") and a **Check missing** button. All three category tags use the brand colour rather than three different ones.

Clicking **Check missing** expands the relevant date selector below that card. Clicking `Ignored (N)` expands the branch's closed dates for restoration. The shared `DaySection` control and the existing close/reopen request flow live in `ImportCompletenessControls.tsx`, so date selection, optional notes, role checks, toasts, and refresh behavior remain consistent with the previous screen. The old `ImportOverviewPage.tsx` table and `ImportCompletenessPage.tsx` page-level display have been removed.

## Tests

`backend/tests/test_import_health.py` covers: Sales flags a high skip rate but not a normal one, ignores tiny batches below the minimum count, and ignores `[recovery replay] `-prefixed batches; Purchase flags two same-branch batches with matching totals but not a different branch's matching total; Inventory requires enough baseline history before flagging, then flags a sparse batch once it has one; slip-total mismatches read back correctly from stored `summary`; dismiss hides a batch and undismiss restores it; dismiss respects branch scoping (404 for another branch's batch); and `build_import_health`'s aggregate counts.

## Known simplifications vs. the original design (intentional, not gaps)

- Purchase duplicate detection uses total-amount matching only, not product-set overlap — see section 2 above.
- Inventory anomaly detection uses product-count only, not an on-hand-quantity-jump check — see section 2 above.
- No historical backfill: sections 2-3 only ever evaluate batches within the requested `days` window going forward — they were not run retroactively over the batches involved in the 2026-08-30 incident (that data was already recovered separately, via the one-off replay-from-`preview_data` script, before this feature existed).
- No in-page recovery action (e.g. "replay this batch") — a flagged batch's fix is still "go to Import History and revert/re-confirm from there," same as Warning's Source Import link. Worth adding later if flagged batches turn out to be common enough that jumping to History each time is friction.
- **"Cross-branch slip numbers" was built, then removed.** It grouped persisted `Sale` rows sharing a `slip_id` across branches and showed them as "Both kept" — purely proof that the 2026-08-30 fix (`sales.slip_id` scoped per branch, not globally) was working, not something needing user action. Cut because it read as an internal correctness check rather than something the page's actual audience — someone deciding whether an import needs attention — would ever act on. If similar "prove the fix works" needs come up again, keep them out of the user-facing page; a one-off script (like the audit used to find the original incident) or a backend test is the right place, not a permanent UI section.
