# Retail dashboard

**There is now a fifth tab, "Overview", in front of these four** — the Branch Health
Score, and later the Early Warning engine, documented separately in
`docs/retail/branch_health.md`. It shows every retail branch at once for an admin account (one card each, then a per-branch detail page), and it is the decision page these four are the evidence pages for:
each of its five dimension scores links into the tab (or, for Data Quality, the Warning
page) that its numbers came from, and it reuses their helpers rather than computing
anything of its own. Two knock-on changes here: `build_inventory_dashboard`'s stock
computation was split into `_stock_summary` so the score can read it without a second
warnings pass, `_cost_totals_and_products` also returns `priced_net_revenue` (the
cost-coverage denominator), and the shared period control now starts at 30d rather than
today because Overview is the tab the Dashboard lands on.

**Status: all four tabs implemented.** (The data-quality tile that once sat on each tab has since been removed — see each tab below.) Revenue shipped first — deliberately, since it's the pillar with no new fields and no caveats — to establish the shared pattern (period control, KPI tiles with vs-previous-period deltas) that Cost, Inventory, and Customer then reused. What exists: `GET /api/dashboard/{revenue,cost,inventory,customer}` (`app/retail/routers/dashboard.py`, `app/services/dashboard.py`) and a tabbed `frontend/renderer/src/components/features/retail/DashboardPage.tsx` (with per-tab components under `dashboard/`), wired into the retail nav as "Dashboard." A layout sketch (HTML mock, not real data) was published as a Claude Artifact during the original design conversation; ask in a new session if the link is needed, since artifact URLs aren't durable enough to paste into a doc that outlives one conversation.

## Period picker — Daily, Weekly, Monthly

The Dashboard's period control offers **Daily** (a chosen day, opening on yesterday), **Weekly** (a chosen Monday-to-Sunday week, opening on last week; a week still running ends today) and **Monthly**, plus the optional custom From/To range. Daily and Weekly are worked out in the browser into an ordinary from/to date range (`usePeriodRange`'s `applied`), so the backend still sees only presets and custom ranges and none of the endpoints changed. The week picker is the browser's own week input; `helpers.ts` converts between its `2026-W38` value and the week's Monday (ISO weeks, the year of the Thursday), covered by `helpers.test.ts`.

**What "vs last year" means depends on the window's length** (`resolve_period`, `WEEKDAY_ALIGNED_MAX_DAYS`). A window of one to seven days — a day, a week, or a short custom range — is compared with the same weekdays 52 weeks earlier (364 days back), so a Wednesday is set against last year's Wednesday and not against a Tuesday or a Saturday, which in a shop whose sales swing by weekday would make the delta meaningless. A longer window (a month, a long custom range) is compared with the same calendar dates, since a weekday no longer matters over that many days. The comparison label under each figure says which: "vs the same weekday last year", "vs the same weekdays last year" or "vs the same dates last year".

## Summary — Recommended decisions

The Summary's "Recommended decisions" card shows the branch's most important Business Alerts (up to three), not fixed advice. It used to be three hard-coded cards ("Clear dead stock", "Purchase selectively", "Protect peak hours") that read the same whatever the data said, so a branch with no dead stock was still told to clear it, and they repeated what Business Alerts already says with real products and quantities. Now `DecisionsCard.tsx` reads the same 30-day Overview request the Business Alerts page makes (one shared cache entry, so no extra fetch when both are opened), keeps the alerts that ask for a decision (critical and warning — "normal" ones are heads-up notes) and leaves out the data-quality ones (fixing a file is housekeeping, not a decision). Each shows just the alert's title and what to do about it (no colour bar; the longer explanation is on Business Alerts), and links to Business Alerts. With none, it says "Nothing needs a decision right now." The summary endpoint no longer returns `recommendations`.

## Revenue — implemented

- **Endpoint**: `GET /api/dashboard/revenue?period=today|yesterday|7d|30d|monthly&branch_id=...` — `branch_id` is required for an admin account (no fixed branch) and ignored for a branch-scoped one (same `resolve_branch_id` rule every other scoped endpoint uses). Scoped strictly to retail branches. `date_from`/`date_to` (both required together, `date_from <= date_to`) override `period` entirely with an explicit custom range — see `resolve_period()`.
- **Response**: branch identity + resolved date range, four KPIs (`net_revenue`, `transaction_count`, `avg_basket`, `quantity_sold` — the sum of every sale line's quantity, in pairs) each as `{value, previous_value, delta_pct}` compared against the immediately-preceding period of the same length (or, for a custom range, the same-length period immediately before `date_from`), a zero-filled daily `trend`, a weekday × hour-band `heatmap` covering business hours only (`HEATMAP_START_HOUR`/`HEATMAP_END_HOUR` = 7–22, one column per hour — parses `sales.sale_time` best-effort; a row whose time doesn't match a handful of common formats, or falls outside business hours, is simply left out of the heatmap, not an error), a `top_products` ranking (each with a qty-weighted `avg_selling_price`, not a plain average of the line-level prices). There is no data-quality box on this tab: bad sale values are on the Warning page and in the Health score's Data Quality dimension, so the tab neither shows nor computes them.
- **Frontend**: period + custom date-range ("Date from"/"Date to") + (admin-only) branch selectors, three stat tiles with a success/error delta badge, a hand-rolled SVG trend chart with a bar/line toggle (`ChartViewToggle`) and weekday/hour heatmap (no charting library added — kept consistent with this project's existing inline-SVG icon approach; both single-hue, sequential-by-value, brand-token-derived per the dataviz method, not a hand-picked palette), a top-products table (with a Selling Price column), and a compact Sale-warnings list.

## Cost — implemented

- **Endpoint**: `GET /api/dashboard/cost?period=...&date_from=...&date_to=...&branch_id=...` — same branch/period/custom-range resolution as Revenue.
- **Response**: `estimated_cogs`, `estimated_gross_margin_pct`, `estimated_margin_per_basket` (each a `{value, previous_value, delta_pct}` KPI), a zero-filled daily `trend` (`net_revenue`, `estimated_cost`, `margin_pct` — the latter two `null` on a day with sales but no priced line at all, `0`/`null` on a day with no sales), a `products` list ranked by **estimated profit** (`estimated_margin`), not revenue — a product with no cost estimate for the period is excluded from this ranking entirely, since it can't be compared by profit — with no data-quality box (that lives on the Warning page).
- **Cost lookup**: `app/services/dashboard.py`'s `_cost_totals_and_products` reuses `point_in_time_buying_price` exactly as `GET /api/sales` and the Warning page do — one pass over the period's sale lines produces the branch-wide COGS total, the per-product breakdown, and the per-day breakdown (for `trend`) together, rather than three separately-computed figures.
- **Frontend**: the three KPI tiles, a "Profit per day" chart (estimated Ks earned each day — net revenue minus estimated cost — bar/line toggle; a day with no sales or no priced line reads 0; deliberately not the daily margin %, which swings wildly when a shop sells only a few pairs a day and turns a no-sale day into a false 0%), a "Top profit products" table (ranked by estimated Ks profit, not revenue). No disclaimer banner is shown on the tab itself — the estimate caveat lives in this doc and in the tooltip/description text instead.
- **Known gap vs. the original design note below**: a duplicated (non-reverted) purchase batch is _not_ specially detected or flagged yet — `purchase_numeric_warnings` still catches bad values on individual lines, but nothing yet flags "this looks like the same purchase file imported twice." Left as a follow-up.

## Inventory — implemented

- **Endpoint**: `GET /api/dashboard/inventory?branch_id=...` — no `period` param, since current stock is a point-in-time fact, not a date-range query.
- **Response**: `as_of` (the latest stock snapshot timestamp for the branch, or `null`), `sku_count`, `critical_count`/`low_count`/`watch_count`, `estimated_stock_value`, `dead_stock_count`, `stock_qty_by_category` (on-hand _quantity_ per category, not value — value silently reads as 0 for any product missing a `buying_price` on its latest snapshot, which would make a category look artificially small), `low_stock_items`, `dead_stock_items`, and `warnings` (the combined `inventory_numeric`/`missing_product`/`reconciliation_uom`/`reconciliation_mismatch` rows, using the business-wide check-window settings since there's no period control here to derive a window from).
- **Days-of-stock**: sales velocity is a fixed trailing 30-day average (`STOCK_VELOCITY_WINDOW_DAYS`), independent of anything selected elsewhere in the dashboard. Status thresholds (`CRITICAL_DAYS_OF_STOCK`/`LOW_DAYS_OF_STOCK`/`WATCH_DAYS_OF_STOCK` = 3/7/14 days) are a reasonable default, not a business-configured setting — a product with zero recent sales gets no computable days-left and simply doesn't appear in the low-stock table (not flagged as either healthy or at-risk). This 30-day figure is the Dashboard's own; the Business Alerts "Urgent reorder" no longer uses it and follows the Reorder page's long-run monthly sales instead.
- **Dead stock**: a separate, longer-window velocity check (`DEAD_STOCK_WINDOW_DAYS` = 90 days, vs. the 30-day window above) — a product lands in `dead_stock_items` when it's still on hand (`on_hand_qty > 0`) but hasn't sold at all in that 90-day window. Deliberately a longer window than "days of stock left," since 30 days with no sale is routine for a slow-but-fine product while 90 days with zero sales is a much stronger "this isn't moving" signal.
- **Frontend**: four stat tiles (no delta badges — there's no "previous period" here; Dead Stock replaced an earlier "Median Days of Stock" tile that was dropped as less actionable). **Estimated Inventory Value** is quantity on hand × buying price (what the shelf cost), and **Potential Sale Value** is quantity on hand × selling price (what it would bring in if all of it sold at its listed price) — both read off the latest count only, and a product with no price on that count adds nothing to that tile, a "Stock on hand by category" quantity bar-list, a low-stock table with a Critical/Low/Watch badge, and a "Dead stock" table.

## Customer — implemented

- **Endpoint**: `GET /api/dashboard/customer?period=...&date_from=...&date_to=...&branch_id=...` — same branch/period/custom-range resolution as Revenue.
- **Response**: `total_transactions` and `conversion_rate` as KPIs (compared with the same dates last year), `busiest_hour` (a plain fact, not a KPI — a bucket has no "up/down vs last period" to compare), `footfall_heatmap` (transaction count, not revenue, same business-hours grid as Revenue's heatmap), `transaction_count_trend` (daily transaction count — the day-by-day footfall trend behind the Customer demand by day & hour heatmap; replaced an earlier `basket_value_trend`, dropped as a near-duplicate of Revenue's own Average Sale Value), `items_per_basket_histogram` (buckets 1–5, 6 meaning "6+"). `conversion_rate` is sales slips ÷ (sales slips + zero-selling visits), counted only on days that have zero-selling records; with none in the period its `value` is `null` and the tile shows "—" — nothing measured is not 0%. The average-items-per-transaction and single-item-share tiles were removed: a customer normally buys one pair, so neither says anything.
- **Frontend**: three stat tiles (the Peak Hour tile has no delta), a "Transaction trend" chart (bar/line toggle), a "Customer demand by day & hour" heatmap (reusing the same `WeekdayHourHeatmap` component as Revenue, parameterized by `getValue`), and a histogram bar-list. The data-quality boxes that used to close the Revenue, Cost, Inventory and Customer tabs were removed; data quality is on the Warning page and in the Health score.

## Frontend structure

`frontend/renderer/src/components/features/dashboard/` holds `shared.tsx` (types, formatters, `StatTile`/`DeltaBadge`, period/custom-range helpers (`periodQueryParams`, `previousPeriodLabel`, `dateRangeLabel`), the generic `TrendChart` (single-series daily bar/line, driven by `ChartViewToggle`), and `WeekdayHourHeatmap`) plus one file per tab (`RevenueTab.tsx`, `CostTab.tsx`, `InventoryTab.tsx`, `CustomerTab.tsx`) — each owns its own fetch/loading/error state so switching tabs doesn't require the parent to track four loading states at once. `DashboardPage.tsx` is the tab bar, a header **Refresh** button (calls `refreshCachedPages()` in `lib/useCachedFetch.ts`, which asks every mounted page to refetch _behind_ the figures already on screen — deliberately not `invalidateCachedPages()`, which empties a page to a skeleton first; its spinner reads the shared in-flight count via `useFetchInFlight()`, since the requests belong to the tabs rather than to the button), plus the shared branch/period/custom-date-range controls (period and date-range are hidden only for the Inventory tab, which has no period concept at all) and renders whichever tab is active.

## Tests

`backend/tests/test_dashboard.py` covers: period math (including the custom `date_from`/`date_to` override), branch resolution (retail-only, admin-requires-branch_id) for Revenue (shared by all four via the same `_resolve_retail_branch` helper), Revenue's KPI/delta values, trend zero-fill, top-products ordering and qty-weighted selling price, heatmap bucketing, and warning-tile branch scoping; Cost's point-in-time cost/margin math, the daily trend's zero-fill and null-when-unpriced cases, and that products are ranked by estimated margin (with unpriced products excluded from the ranking, not sorted as 0); Inventory's stock value, category quantity rollup, low-stock status/velocity math, and dead-stock detection (including that a sale just outside the 30-day velocity window but inside the 90-day dead-stock window correctly excludes a product from dead stock); and Customer's basket-stats/histogram math and transaction-count trend.

## Design notes (for context — all four pillars above are now implemented against these)

## Scope: one branch at a time

This is not a cross-branch rollup. A retail user sees only their own branch (`users.branch_id`, the same scoping rule `imports.py`/`data_quality.py` already use); admin has no branch and gets a branch selector, but still views one branch at a time — an all-branch aggregate view was considered and deliberately deferred as a separate, later feature. Only retail branches are included in the branch selector and overview cards (the Wholesale branch is excluded).

## Four pillars

The dashboard is organized as four tabs: **Revenue**, **Cost**, **Inventory**, **Customer**. The Customer tab is _not_ customer-level tracking — the retail sales pipeline has no customer identifier anywhere. `Sale` (`app/retail/models/sale.py`) carries only `slip_id`/`slip_number`/`sale_date`/`sale_time`/`location_raw` — a POS slip is structurally anonymous. The wholesale workflow, which does have customer-named orders (see [wholesale/](../wholesale/)), is a deliberately separate business line (see CLAUDE.md) and out of scope here either way — its data never touches these tables. If real customer-level tracking (repeat visits, loyalty) is ever wanted, that's a POS/data-capture decision upstream of this dashboard (a loyalty card, phone number, or membership ID captured at the point of sale) — not something this tab fakes from existing tables. Instead, the Customer tab reframes the same anonymous slip data Revenue already uses as **basket/visit behavior** — a proxy for "customers," not an identity.

Each pillar's original design notes (period control choice, which existing plumbing to reuse, caveats to surface) now live in its "— implemented" section near the top of this doc, alongside what was actually built and any place the implementation diverged from or narrowed the original note (e.g. Cost's duplicated-purchase-batch detection, still a follow-up).

## Aggregation endpoint decision (resolved)

Settled while building Revenue, and followed for the other three: **one endpoint per pillar** (`GET /api/dashboard/{revenue,cost,inventory,customer}`), each parameterized by `branch_id`+`period` and returning that whole tab's pre-aggregated payload in one response, rather than one endpoint per individual widget or a single endpoint switched by a `pillar` param. Reasoning: the four pillars don't share a single query shape (Inventory doesn't even have a period control), a per-pillar endpoint keeps each one's aggregation logic (and tests) independently readable, and a whole-tab payload means the frontend fires one request per tab switch instead of 4-6 parallel ones. `app/services/dashboard.py` holds the aggregation helpers; add each new pillar's functions there rather than starting a second service module, so date-range/period logic (`resolve_period`) stays shared.
