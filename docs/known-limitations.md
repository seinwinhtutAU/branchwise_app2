# Known limitations

Things that are known gaps, deliberately deferred rather than oversights.

- **Self-service sign-up still doesn't create an app profile.** The app's own Sign Up form (`POST /api/auth/signup`) still only creates a Neon Auth account, not a corresponding `users` row, so a self-signed-up account can authenticate but gets a 404 from `/api/me` and can't do anything. This is no longer the whole story, though: admin can now fully provision an account (both the Neon Auth login and the `users` row, in one step) from **Settings → User Management** in the app itself — see [auth-and-accounts.md](./auth-and-accounts.md) — so the earlier "only the seeded accounts are provisioned, and only by running a script" limitation is gone; what remains is that a stranger can't onboard themselves without an admin doing that step for them, which is intentional for a business-internal tool.

- **Purchase import isn't idempotent.** `purchase.csv` has no natural per-batch key in the source data, so every confirmed import creates a new `Purchase` batch — re-uploading the same file double-counts. Will need real purchase-order references/dates from a richer export to fix properly.

- **`purchases.purchase_date` is a placeholder.** Set to the import date, not a real purchase date, since the source file doesn't have one yet.

- **"Current stock" has a real endpoint now; "current cost" still doesn't, as its own query.** `GET /api/inventory` (`app/retail/routers/inventory.py`) computes current stock — the rows from the branch's latest `stock_levels` snapshot — so that half of this used to be true and no longer is; see [database-schema.md](./database-schema.md#not-yet-built) for the up-to-date state. Cost has no equivalent standalone endpoint: `app/retail/services/pricing.py`'s `point_in_time_buying_price` prices a product as of a given date (see the bullet below), but it's only ever called inline, per sale line, by `GET /api/sales`, `GET /api/data-overview`, and the Warning page's sale-numeric check — there's no "what does this product cost right now" query independent of a specific sale's date.

- **Sale-line cost is priced as of the sale's own date, each backward lookup bounded by its own staleness window, with one further bounded exception for recount lag.** `app/retail/services/pricing.py`'s `point_in_time_buying_price` prices each sale line using whichever purchase price was already on record as of that sale's date — not whatever the latest purchase price happens to be today, which would silently re-price old sales every time a new purchase comes in and distort any margin trend over time — but only if that purchase price is dated no more than `purchase_lookback_window_days` before the sale (default 14); an older purchase price is treated as too stale to trust, the same as no price at all. If no _usably recent_ purchase price exists, it falls back to a stock-snapshot price as of that date, bounded the same way by `stock_lookback_window_days` (default 7). If even that doesn't exist, it falls back once more to a stock snapshot recorded up to N days _after_ the sale — N is `stock_forward_fallback_window_days`, default 30 — since a missing-stock-code fix is normally "recount it," and recounts are manual, physical work on their own cadence that routinely lags the sales it would price — that later recount is often the only cost this product will ever get for sales just before it. Purchase price gets no such forward look, since purchases are timely enough that reaching into the future would reintroduce the same distortion this design avoids. All three windows are admin-configurable business settings (`GET`/`PUT /api/settings`, backed by `app.services.settings`'s `AppSetting` key-value store; `app/retail/services/pricing.py`'s `PURCHASE_LOOKBACK_WINDOW_DAYS`/`STOCK_LOOKBACK_WINDOW_DAYS`/`STOCK_FORWARD_FALLBACK_WINDOW_DAYS` are only the fallbacks used when a caller doesn't fetch the configured values, e.g. tests). If a sale line misses all three windows, cost is `(None, None)` — a stale price is never silently used just because it's the only one on record. The function returns `(price, source)` — `source` is `"purchase"`, `"stock"`, or `"stock_forward_fill"` — and `GET /api/sales`, `GET /api/data-overview`, and the Warning page's sale-numeric check all expose it as `Buying_Price_Source`/`_BuyingPriceSource`, so a forward-filled estimate no longer looks identical to an exact point-in-time match; no frontend renders that field differently yet, though. This is still only as trustworthy as the purchase data feeding it, which inherits the idempotency gap below.

- **Branch resolution has no explicit mapping.** The CSVs' `Location` field doesn't correspond to branch names and isn't used for anything beyond audit (`location_raw`) — branch is resolved from the uploading user's own account instead. If a single account ever needs to import for multiple branches, this will need revisiting.

- **The old wholesale workflow was deleted and rebuilt from scratch — this is historical, not a current gap.** On 2026-09-11 the original customer-orders/factory-vouchers workflow (models, routers, services, screens) was deleted pending a redesign; migration `b7e4d0c91a52` dropped the five tables it used, which held only test data. It has since been rebuilt, screen by screen, into the workflow documented in [wholesale/](./wholesale/) — see that folder for the current, much larger feature set (Customer Orders, Supplier Vouchers, Shipments, Receiving, Inventory, Finance, and more). `app/retail/routers/inventory.py` was never affected by any of this — it's `GET /api/inventory`, the retail current-stock-per-product view, an unrelated name collision with the wholesale Inventory screen.

- **Electron CSP allowlist is manual.** Any new external host the renderer needs to reach must be added to the `connect-src` directive in `frontend/renderer/index.html`, or the request fails silently.

- **The Warning tab's daily inventory reconciliation assumes one consistent unit per product.** `GET /api/warnings` (`app/retail/services/data_quality.py`) compares a branch's latest inventory snapshot against `previous snapshot + purchases − sales` since then, but `SaleLine.uom`/`PurchaseLine.uom` are free-text with no conversion table, and `stock_levels` has no unit at all — if a product's sale/purchase rows use more than one UOM string in the window, the math may silently mix units. This is flagged as a separate (non-critical) "unit mismatch" warning rather than solved, since a real fix needs a per-product unit-conversion table. It also relies on `purchases.purchase_date` being the import date (see above) — the reconciliation window is really "since the last inventory import," not calendar dates from a purchase order.

- **The standalone Checking (physical stock audit) page is no longer in the app.** The `/api/checking` endpoints still exist and the old `CheckingPage.tsx` has been deleted; staff use the Physical stock audit alert on Business Alerts instead. See [checking.md](./retail/checking.md).

- **Reconciliation "expected" is only as trustworthy as its inputs.** The comparison in the bullet above (prior snapshot + purchases − sales) breaks down if the prior snapshot was itself wrong, or if a purchase/sale file for that window was never imported — in both cases the "expected" number is wrong, not the new count. `inventory_reconciliation_warnings` mitigates this rather than solving it: gaps under `RECONCILIATION_MISMATCH_THRESHOLD` (2 units) are treated as routine noise and not flagged at all; when there was zero purchase/sale activity recorded for a product in the window, the message points at a likely missing import instead of telling staff to recount; and a negative "expected" (which can never be a real stock count) gets an explanation instead of being shown as a target number. There's still no way to detect "the prior snapshot itself was wrong but there _was_ purchase/sale activity" — that case still produces a "recount" message that may be pointing at the wrong thing.
